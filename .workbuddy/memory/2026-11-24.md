## 墨山插件协议 v2.0 设计（产出，未改动中台）

背景：用户要做「点一下装上」的插件市场，且插件本质多为「几个开源软件 + 胶水 + 简易中台 + 可视化连线说明」。

调研结论：
- **Obsidian 的机制最省事**：索引是 `obsidian-releases` 仓库里一个 `community-plugins.json`（一条仅 `id/name/author/description/repo`+可选 `branch`），客户端拉各插件 repo 的 `manifest.json` 取版本号，再按同名 GitHub Release tag 下资产。**零后端、零 CDN**。另有 `versions.json` 做宿主版本回退、`community-plugin-stats.json` 统计下载。
- **CasaOS** 证明「商店本身只是一个 URL」：`store-config.json` 只有 `store_id/name/description/maintainer/url`，故可多商店源。
- **Runtipi**（runtipi 9747★ / appstore 503★）有 `app-info-schema.json`，字段与本地插件高度同构。
- **Umbrel**（794★）的 `permissions: [STORAGE_DOWNLOADS, GPU]` + `folderAccess` 是最清楚的权限声明范式。
- **Agent Plugins 1.0.0**（2026-08，agent-plugins.org，Vercel 发起，AWS/Cursor/Microsoft/OpenAI 在 TSC）：目录 + `plugin.json`，必填仅 `$schema`/`name`，共 10 个顶层字段，`extensions` 按反向域名给客户端私有数据。哲学可抄。
- 反向证据：Dashy / Homarr / Homepage / Glance **均无第三方插件协议**，只有内置 widget。该细分领域是空缺，只能自定。
- Open VSX（2077★，Java+Postgres）仅在未来真要开放投稿时才需要。

设计决定（写入 MOSHAN-PLUGIN-SPEC.md）：
1. 四对象：Registry（静态 JSON）/ Package（moshan.json）/ Component / Wire；Card 形状单独固定。
2. `kind` 三分支：`single` 自带进程、`stack` 组合上游、`adapter` 包装已有服务。
3. **wires 为唯一真源，一份数据三用**：渲染拓扑图（mermaid）+ 连线说明表 + 安装时 env 注入。
4. 有 container 时编译成标准 `compose.yaml`，不自己造编排器。
5. 端口池 8790–8799；`manifest` 可演进但 `_工作台/plugins.json` 冻结，`dash.html` 不改。
6. 安装 9 步（resolve→download→verify sha256→extract→validate→plan→apply→probe→register），任一步失败必须完整回滚。

产出文件（工作区 `2026_11_24_16-30-17`）：

## 墨山插件协议 v2.1：搭建层（同日晚追加）

用户新增需求：不止插件市场，还要能做「搭应用」——流程图上每个格子填功能，AI 推荐里面放什么开源软件；开源软件可拆成功能模块，按需取用。

设计（已实现并跑通）：
- **核心决策：格子里填能力（capability），不填软件名。** 受控词表 18 条（media.download / media.library / note.store / search.fulltext / ai.usage / automation.glue …）。理由：填软件名则推荐无从发生；填能力才能打分、校验、推导连线、给理由。AI 只处理词表之外的模糊需求，落表后匹配必须确定性。
- **软件拆模块**：一个 entry = 若干 module，module 声明 `capability` / `port` / `accepts(cap→env)` / `shared(共享卷)` / `config` / `cost` / `requires`。三条规矩：能独立开关、必须声明代价、不许改上游行为。
- **连线自动推导**：`provides ∩ accepts` → env 注入；`shared` → volume；都不匹配 → 报错并建议加胶水格。
- **协议升到 spec 2.1**：`wires[]` 新增 `carrier: env|volume`。原因：qBittorrent 与 Jellyfin 共享的是**文件**不是 URL，旧模型硬注入 `LIBRARY_URL` 会生成「看着通实际不通」的表。validate.py 已拒绝「volume 连线带 env」。
- **模块显式勾选即为准**：`use.modules` 非空时不再自动补 needs，允许出现缺口（否则用户取消勾选会被静默加回来 —— 实测踩到）。Python 与画布两侧同规则。

产出（工作区 `2026_11_24_16-30-17`）：
- `schema/blueprint.schema.json`、`schema/catalog.schema.json`
- `catalog/moshan-catalog.json`（18 能力 / 13 软件，真实镜像与端口）
- `examples/blueprint-media.json`、`blueprint-knowledge.json`、`blueprint-gap.json`、`generated-*.moshan.json`（产物，勿手改）
- `tools/blueprint.py`（解析器：推荐打分 → 选模块 → 端口分配 → 推导连线 → 生成清单 + mermaid）
- `canvas.html`（单文件可视化画布，内嵌目录与蓝图，离线可用；改 UI 改 `canvas.template.html` 再跑 `tools/build_canvas.py`）

修掉的真实 bug（三处，均由实测暴露）：
1. 主入口端口 8790 被普通格子抢走 → 先保留 install.port。
2. 无效能力（不在词表）仍会选出软件 → 无有效 need 直接跳过并报错。
3. env 型连线误把「不读环境变量的组件」当 custom 处理 → 改为仅 `_custom` 标记的组件可接任意能力，其余报错建议改卷。
4. 画布 SVG 用 viewBox 缩放导致连线与卡片错位 → 改像素 1:1 映射；跨卡片连线走下方弧线，否则被中间卡片盖住。

实测：`python3 tools/validate.py examples/*.json catalog/moshan-catalog.json` → 10/10；两个蓝图解析出的清单均通过校验（3 组件/3 连线、5 组件/4 连线）。推荐可解释样例：采集格 `wechat-scholar`(30MB) 胜过 `rsshub`(300MB)，理由是「同覆盖，省 270MB」。

## 23:59 架构库：模块脱离软件独立（commit 9be2ea3）

**用户要的东西**（一句话概括）：「Dify 拆出来那 6 个模块，别的软件也该能复用」——即软件不是一个个孤立条目，而是**若干可复用模块的组装**。最终目标：用户输入需求 → 匹配一套架构 → 逐格挑方案 → 自动出功能建议。

**数据模型（关键决定）**
- `arch/arch.json`，两张表：`components`（模块库）+ `products`（软件=组合）
- 层级靠 `parent` 串，`level` 由脚本推——**不让手填**，填错必然静默腐坏
- 允许 `parent=null` 的 `kind=module`：小 skill 只有一层，不该硬塞进某个域
- 子模块（`part`）不必单独挂在软件上：父模块被选，它自然在里面（统计时按隐含覆盖算）

**provider 四类，这是这次最重要的设计**
| kind | 含义 | 例子 |
|---|---|---|
| oss | 开源可自部署，必须有 repo 才可核许可 | Chroma / pgvector / Docling |
| commercial | 闭源商用 | 可灵 API / Cursor |
| build | AI 自己写，**必须给 effort + tokens + outline** | 「AI 自己写 4–6 天 / 约 350 万」 |
| pattern | 零依赖的现成做法，不引项目 | RRF 融合 / 直接提示词规划 |

**铁律写进校验**：某格若全部方案都闭源，必须补一条 `build`，否则用户走到这格就是断头路。同样，只有单一闭源方案的模块直接报错。

**实测结果**：45 模块（8 域 / 32 模块 / 5 子模块，3 层）、123 方案、30 软件、**复用率 86%**。复用最多的是模型网关 19 个软件、执行主循环 13 个、向量检索 11 个——**网关和 Agent 循环就是这轮 AI 产品的水电煤**。

**工程约定**：数据写在 `arch/parts/seed0N.py`（分批），`gen.py` 合并成 JSON；`build.py` 校验 + 建 SQLite（component/provider/product/composes 四表）。arch.db 是产物，进 .gitignore。加批次只改 gen.py 一个 import。

**下一步（未做）**：需求→架构的匹配引擎。思路：给每格补「适用场景关键词」，用户需求进来先分词打分选域，再在域内逐格给 2–3 个候选，输出可编辑的架构草案。
