# 架构库（arch）

把「一个软件」拆成「若干可复用模块的组合」，并让同一模块在整个库里被反复引用。
硬件也走同一套：**自己做一台设备**（不是给现成设备写软件，那是 `app.edge`）同样拆成可选的格。

## 三张表，一条规则

```
本体域 domain ── 模块 module ── 子模块 part      （层级靠 parent 串，level 由脚本推）
                                                        │
软件 product ── 组合 composes ──────────────────────────┘  （用了哪几格 + 选了哪款 + 必需/可选）
                     │
               方案 provider  （oss 开源 / commercial 闭源 / build 自研 / pattern 零依赖做法）
```

一条强制规则：**任何一格若全部方案都闭源，必须补一条 `build`（AI 自研，带天数、token、步骤）**，
否则用户走到这格就是断头路。校验器会拦。

## 硬件那一半（第 6 批）

自己做一台设备的 10 个决策格 + 3 个子模块：

```
hw 硬件（真机）
 ├ hw.mcu        主控与模组        选它就定了功耗、成本、认证难度
 ├ hw.sense      传感与采集        读数准不准，一半是结构问题
 │  └ hw.sense.calib     校准与补偿
 ├ hw.display    显示与交互        墨水屏刷完就断电，策略比驱动重要
 │  └ hw.display.refresh 刷新策略
 ├ hw.power      供电与续航        任一漏电项都能让续航从 4 年变 3 个月
 │  └ hw.power.deep      低功耗策略
 ├ hw.wireless   无线与协议        接哪个生态，反着选一定后悔
 ├ hw.firmware   固件与 OTA        没留 OTA = 装到墙上后再也改不了
 ├ hw.pcb        电路与打样
 ├ hw.enclosure  结构与外壳        壳决定读数准不准，不是外观问题
 ├ hw.gateway    数据落地          软硬交界，选错后面全返工
 └ hw.cert       认证与量产        SRRC/CE、电池运输、批量烧录
```

和 `app.edge` 的边界：**`app.edge` = 手上已经有一台设备，软件去接它；`hw.*` = 你要造一台出来。**
两者可以同时出现（自制的盒子 + 已有的扫码枪），不冲突。

接口基板为硬件加了 4 个类型：`M` 测量读数、`P` 电源、`W` 固件、`B` 板卡/结构工程。
为什么不能复用 `R`（记录）：读数带单位和时间戳，消费者是屏和主控而不是数据库；
硬塞进 `R` 会让 `app.data` 误判成「有记录就必须存库」。

## 中台本体那一半（第 7 批）

「给自己做个个人中台」这类需求，原来的 app 域只有 data / auth / ui / file / edge——那是「一个网页应用」的地基。
常驻桌面、托盘点开、剪贴板历史、待办提醒、可装扩展、自动更新、手机同步，这些一格都对不上。补 7 格：

```
app 应用底座
 ├ app.window   桌面外壳与托盘    选错（或先做成网页）＝系统调用全部重写
 ├ app.todo     待办与提醒        周期规则写错＝每月堆逾期副本，用户不再打开
 ├ app.clip     剪贴板历史        采样方式选错＝图片丢失或常驻 300MB
 ├ app.launch   快捷启动器        只支持 exe 不支持 .lnk/.desktop＝一半图标空白
 ├ app.plugin   扩展系统          一开始不留 manifest＝以后加插件等于重构
 ├ app.update   自动更新          不做验签＝你发的每个版本都可能是别人塞的
 └ app.sync     多端同步          先不做加密＝服务器被看就是全裸
```

接线（`wires.py`）：

| 格 | 吃 | 吐 | 为什么这么钉 |
|---|---|---|---|
| `app.window` | — | X 界面 | 壳体自己就是入口，不依赖任何上游 |
| `app.todo` | — | R 记录 | 待办是纯记录源，先立起来再谈别的 |
| `app.clip` | — | R 记录 | 监听系统剪贴板，同样不需要上游 |
| `app.launch` | R | Q 动作 | 没有资源清单就无从启动 |
| `app.plugin` | X | X | 扩展挂进宿主界面，产出的也是界面 |
| `app.update` | X | E 事件 | 只在界面上报「有新版/下载中」，不参与数据流 |
| `app.sync` | R + X | R | 要记录才能同步，要界面才能配对扫码 |

三种「中台风格」的实测（`base.check`）都是 **0 断点 0 死端**：

| 风格 | 模块 | 格 | 连线 |
|---|---|---|---|
| 极简 | 2（外壳、数据仓） | 3 | 3 |
| 中等 | 6（+ 搜索、待办、速记、AI） | 9 | 10 |
| 功能齐全 | 11（+ 剪贴板、启动器、扩展、更新、同步） | 14 | 15 |

这条路和「一句话需求」是两条入口，但走到底汇到同一个连通检查：
**中台模块只是产品视角的勾选，真正装的是它摊开的能力格。**
前端在 `app.template.html`（`HUB` 数据表 + `viewHubStyle / viewHubMods / viewHubPlans` + `pcbHTML` 插模块动效）。

## 场景、包、胶水（第 8 批）

第七批只回答了「一个常驻桌面的软件」要什么。但用户真正要做的还有仓库、跨境电商、无人机、
放置游戏、生图台、移动热点——它们和中台共用的只是「数据 + 界面 + 外壳」，剩下的全是各自的。
所以第八批补了 31 格、四个新域：

```
biz  交易与库存   商品 / 库存 / 订单 / 支付 / 物流 / 会员
game 游戏运行     主循环 / 存档与离线结算 / 数值 / 商店
map  位置与地图   底图 / 定位与坐标系 / 轨迹与围栏
ops  运行与运维   部署 / 监控 / 告警
app 补十二格      看板 / 知识地层 / 日历 / 提醒 / 主题 / 事件总线 / 后台任务 /
                  进程通信 / 数据契约 / 备份迁移 / 自动化触发 / 分享协作
hw  补三格        扫码 / 蓝牙 / 配网
```

### 为什么按「包」出现

一格里讲的是「选错了要返工什么」，一个包里讲的是「这件事成套出现」。
用户不会想「要不要 app.board」，只会想「要不要看板」。所以包是**分组与默认值**，
不是新的一层数据：`PACKS` 只写名称、色相、等级，模块靠 `pk` 字段归队。

等级只在包的层面判默认（必装/推荐包默认勾），场景可以**把一个可选包提升成核心包**：

```js
{id:"wms", packs:["core","biz","data","hw","ops"], must:["core","biz"]}
```

「仓库管理」里交易包是核心，「个人中台」里它是可选。同一份数据，两种语义。

### 三个新概念

| 概念 | 回答什么 | 落在哪 |
|---|---|---|
| 包 | 这件事要哪几件一起上 | 15 个，带色相，模块卡跟着上色 |
| 胶水 | 模块之间怎么接 | 10 项，每一项对应一格（`app.bus` / `app.ipc` / `app.schema`…） |
| 底座 | 整台东西跑在哪、怎么发出去 | 9 项，对应 `app.window` / `app.data` / `ops.deploy` 等 |

胶水与底座不是「第四类模块」，它们是**同一批格子的另一种说法**：
`app.bus` 既是「事件总线」这一格，也是装配台里的「胶水 ① 事件总线」。
这样前端多了一层选择，底层口径完全不变。

| 个人中台 | 3 模块 / 4 格 | 17 / 17 | 30 / 25 |
| 仓库管理 | 3 / 4 | 12 / 12 | 28 / 28 |
| 跨境电商 | 3 / 4 | 17 / 16 | 35 / 32 |

### 这一批踩到的坑

1. **模块 id 撞名**。硬件包想叫 `board`（板子），笔记包已经有 `board`（看板）。
   `hubMod("board")` 返回第一个，于是「装一块板子」实际装上了看板，连通检查报「缺板卡工程」。
   现在硬件那个叫 `pcb`。**跨包新增模块前先查 id**。
2. **默认勾选读到上一个场景**。`defaultMods()` 里算「这个模块在这个场景里算不算推荐」时读了
   `S.hub.scene`，而调用点正在构造新的 `S.hub`——读到的是旧值。改成显式传 `sceneId`。
3. **两条真断点被设计掩盖**。`hw.sense` 原本要「电源 + 板子」，`hw.provision` 要「固件」。
   软件视角下这两条不成立（串口读的是已有设备、配网软件不担保固件），
   放宽成 `[]` 与 `[["X"]]` 后才通过——放宽的同时在 `wires.py` 里写了为什么。
4. **死端会吵**。全文检索产 `C`，没人接就报「做出来没去处」。但它同时产 `X`（结果摆在界面上），
   改成「有任一终点型产出就不算死端」。

## 200 个软件从哪来

前 30 个是手拆的（Dify、n8n、RAGFlow、Cursor…），后 170 个来自 ai-bot.cn：

1. 抓 14 个分类页 → 去重得 1376 个候选；
2. 按分类分层抽样（写作 15 / 图像 17 / 视频 18 / 办公 19 / Agent 15 / 聊天 10 / 编程 12 /
   设计 13 / 音频 12 / 搜索 9 / 框架 12 / 模型 9 / 检测 6 / 提示词 6）；
3. 只保留详情页有 ≥6 条功能点的（占位页、只有「相关工具」列表的剔除 24 个）；
4. 抽到的正文存 `data/aibot-200.json`，作为可复算的证据，不引原文进库。

**许可一律标「未核」。** 这个站 85% 是闭源 SaaS，站方写的「开源」也不可信（实测 n8n 是
Sustainable Use、Dify 是 Apache-2.0 加附加条款）。要进下载集必须逐条回源，那时才改字段。

## 组合是推出来的，不是手写的

170 × 5 格 ≈ 850 条关系，手写必然不一致。规则写在 `parts/seed04.py`：

- **强词命中 → must**（如「抠图」「数字人」「降 AIGC」）
- **弱词 → optional，最多补 2 格**（如「模板」「发布」）；弱词**永不升级**为 must
- **域门禁**：`CAT2DOM` 限定某类产品只能挂哪几个域。没有这道闸，企业搜索会挂上
  「角色与陪伴」「小说与剧本」——词面能对上，语义完全无关
- **上限 8 格**：再多就不是拆解，是堆砌

改一条词就能全库重算，这是选择规则而不是手写的唯一理由。规则推不出的例外，在
`OVERRIDE` 之外靠调词表解决——目前没有单独的人工修正表。

## 用法

```bash
python3 arch/parts/gen.py            # 合并 parts/seed0N.py → arch.json
python3 arch/build.py                # 校验 + 建 arch.db + 打统计
python3 arch/build.py --tree kb      # 某棵子树
python3 arch/build.py --comp kb.rag  # 某格的全部方案
python3 arch/build.py --product dify # 某软件由哪些模块拼成
```

`arch.json` 进版本库（可 diff、可 review），`arch.db` 不进（随时重建）。

## 交付：先试用，再打包

中台装完不是终点，后面还有两步，都做在 `app.template.html` 里。

**`#/trial` 试用**　把选中的模块拼成一个**能点的**模拟中台：左侧是模块导航，待办能加能勾、
速记能存、搜索能跨待办/笔记/剪贴板找、AI 对话框能真的给你加一条待办、剪贴板能复制、
扩展开关能拨、更新和同步有假进度。数据存在浏览器里，随时「重置试用数据」。

**`#/pack` 打包**　生成 zip，四个文件：

| 文件 | 内容 |
|---|---|
| `index.html` | 刚才试的那个中台，双击即开，零依赖零网络 |
| `manifest.json` | 风格、模块、每块选的方案与理由、能力格、施工顺序（机器可读） |
| `README.md` | 怎么用、装了什么、施工顺序、三个提醒（给人看） |
| `模块清单.md` | 按能力格展开的施工表（`mdText()` 产出，与「导出清单」同一份） |

两个关键决定：

1. **试用和打包共用 `trialDoc()`**。它返回一份完整 HTML 字符串：试用页塞进 `iframe.srcdoc` 跑，
   打包时原文写进 zip。这样「试的」和「带走的」不可能分叉——改一处两边同时变。
2. **zip 是手写的**（store 模式 + 自算 crc32，约 70 行）。不引 JSZip 之类的外部库，因为这份
   单文件 HTML 要能在断网、`file://`、沙箱 iframe 里都跑起来。文件头 `flag=0x0800` 声明 UTF-8，
   中文文件名才不乱码。

模拟范围写清楚了，不装作能用：界面对、交互对、**后端是假的**。`index.html` 里的 localStorage
就是 `app.data` 那一格的替身，真做的时候换成 SQLite 单文件。

## 两条线合成一条

以前「个人中台」和「一句话需求」是两套页面、各走各的步骤条，入口也散在侧栏和首页各一处。
现在共用一套壳，只有步骤内容不同：

| 路线 | 步骤 | 落地页 |
|---|---|---|
| 场景装配 | 场景 → 风格 → 包 → 方案 → 确认 → 组装 → 交付 | `#/hub-scene` `#/hub-style` `#/hub-mods` `#/hub-plans` `#/confirm` `#/build` `#/trial` `#/pack` |
| 一句话需求 | 写需求 → 选型 → 确认 → 组装 → 完成 | `#/new` `#/plan` `#/confirm` `#/build` `#/done` |

- `hubSteps(n)` 是七项（场景/风格/包/方案/确认/组装/交付），`topbar()` 的 `steps` 参数接字符串
  就原样塞进去——以前确认页把步骤条拼进了面包屑里，现在统一走这个参数。
- 左侧「当前装配」由 `renderNav()` 现算：有装配就走七步链，没有就走需求链，并留一个
  「开个中台」入口。当前页高亮、走过的打勾。这样新加的流程并进了同一条导航，
  不是另挂一个菜单项。
- 两条线共用 `check()`（断点 / 死端 / 施工顺序），所以做出来的东西是同一个口径。

## 草稿：把没做完的存下来

`S.drafts` 是个数组，每份 `{id, nm, kind, at, route, need, picks, sels, hub}`。存的时候只拍快照。

| 环节 | 做法 |
|---|---|
| 入口 | 任意步骤顶栏的「存草稿」（`topbar()` 自动加；`home` / `lib` 不加） |
| 命名 | 默认「个人中台 · 中等 · 6 模块」或需求前 22 字，可改；同名再存＝覆盖 |
| 落点 | 工作台「草稿箱」：`中台 · 6 模块 · 9 格`、停在哪一步、多久之前；整行可点恢复 |
| 恢复 | `draftOpen()` 拷回 `need/picks/sels/hub`，按存的 `route` 跳页 |
| 换机器 | 草稿箱「导出」存成 `墨山草稿.json`，「导入」按名字合并（同名覆盖） |

两个坑值得记下来：

1. **组装/交付是过程态，不存**。`S.build` 里有计时器和模拟进度，存进草稿既无意义又会在
   恢复时跑出一个假的「正在组装」。所以恢复 `#/build` `#/done` 一律退到 `#/confirm`。
2. **`S.picks` 在中台模式下是派生值**，由 `hubCells(mods)` 摊开。所以 `viewHubMods()` /
   `viewHubPlans()` 一进来就重算，否则上一次「一句话需求」的格会串进来（表现为草稿显示
   「0 格」或格数对不上）。

存储降级也补了一层：沙箱 iframe 里 `localStorage` 会抛 `SecurityError`，`save()` 除了记内存，
还会把整份状态写进 `window.name`（同一标签页刷新后还在）；设置里如实显示当前用的是哪一种，
并提示「要长期留着请导出草稿」。
